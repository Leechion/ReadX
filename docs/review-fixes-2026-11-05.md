## 续作：F2 / F3 / F4

- **F2**：SQLite 适配器使用条件 UPDATE / INSERT。只有读到的旧值仍是当前值才提交；发生冲突时重读并重新计算，最多尝试 16 次，持续冲突会明确报错。这样也能处理同步事务等裸 SQL 写者，而无需把会查询数据库的业务校验回调包进事务，避免单连接自锁。可重试回调的分类状态及文档元数据临时值每次重新初始化。现有同步事务内快照复查继续保留。
- **F3**：`beginImportJob` 在 `jobsMu` 内拒绝同 key 的运行中任务；文件上传、EPUB 以及 arXiv 附件入口在拒绝时不启动 worker、不覆盖原取消句柄。取消后的任务先进入等待 worker 退出的状态，实际收尾前不接受同 key 重试；旧 worker 收尾后允许重试。取消句柄交接如果遇到已取消任务，会立即取消新上下文。
- **F4**：Lee 导入、后台翻译/渲染、OCR 归一化，以及两处 RPR 调用共用 `internal/proctree`。Windows 取消时执行隐藏窗口的 `taskkill /T /F`；非 Windows 使用独立进程组并向整个组发送终止信号。设置命令退出等待上限，避免遗留管道无限阻塞。

验证：条件写入测试强制交错两个独立 Store 和同步式裸 SQL 事务，确认两边修改都保留，且回调内查询数据库不会自锁；12 个并发同 key 请求只有一个获准；重复文件上传接口不进入 OCR；原取消句柄不被替换，取消尚未收尾时不能重试。进程测试实际启动父子进程，取消后确认子进程停止写入。原有元数据并发、回收站恢复、同步往返、导入历史及取消测试通过。Windows 上验证了进程树取消；macOS 源码同步更新，未作 macOS 实机验证。

范围说明：未将所有裸 `app_state` SQL 迁移至统一 Store；本次修复的是元数据读改写与这些写者交错时的覆盖问题。同 key 导入登记保护限于同一服务进程；不提供多服务实例共享作业目录的协调。不同 UUID 的重复重翻译（报告 F12）仍是单独问题，未在此项中宣称解决。
