## 1. 目标和估算前提

目标是打通“外部发现 → 有授权地采集与处理 → 研究沉淀 → 对外交付”，沿用现有单人、本地优先、Windows 权威源码与 macOS 镜像的架构。

以下作为排期假设，而非已确认的用户要求：一名熟悉当前代码的全栈开发者；每周五个工作日；使用已有 Go、React、Electron 技术栈；首版浏览器扩展支持 Chrome／Edge；不建设云端账号与多人实时协作；不把本地文件备份当成分享格式。

“按库”首先指一个数据根对应的书库；现有“书架”是分类，不直接视为独立数据根。权限还需支持书架和单篇文档，以覆盖同一书库混放公开论文与未发表材料的情况。LaTeX 项目单独关联策略，不能假定所有项目都有论文归属。

库与权限作用域使用持久化 ID，而非绝对路径或可修改名称。现有书架分类需要补稳定身份映射，改名、移动或恢复备份不能悄悄丢失策略。一次性授权绑定设备／会话和期限，不能随同步或分享自动变成另一设备的发送许可。

工作量包含代码、接口契约、迁移、针对性测试和使用说明；跨平台运行验证包含在交付要求内，但本机尚未具备的 macOS 实机验证资源是排期依赖。扩展商店审核、第三方接口变更及平台签名发布等待不计入开发人日，也不承诺审核通过日期。

## 3. 共用基础与依赖

六项共用三类基础，不各自建立一套文献或任务系统：

1. **处理授权**：按动作、材料、目标服务生成发送说明并校验权限；外部检索词、题录查询也计入相关数据流。
2. **文献身份与来源**：保留原始来源记录、规范 DOI／PMID／arXiv ID、版本及本地文档关联；同一论文可以有多个来源和多个文件版本。
3. **异步任务**：沿用已有任务进度和取消机制，新增分页游标、失败项与幂等键；不能只为新功能另开一套内存任务表。是否需要任务注册表迁移，应基于能力差异单独决定。

## 4. P0：外部服务的按库授权与数据流清单

### 4.1 首版交付边界

策略覆盖书库、书架、文档及 LaTeX 项目，按数据类别和处理目的授权。动作至少区分：公开题录查询、OCR、翻译、问答／精读、图表分析、演示稿、LaTeX 助手与源码修改、第三方回写、同步和分享。

需要区分“外部通信”“向配置的模型发送内容”和“将材料交给子进程”。不能用 URL 是 localhost 就保证计算在本机：本地代理和 CLI 仍可能调用云模型。

| 场景 | 默认决策 |
| --- | --- |
| 新建敏感书库／敏感书架 | 拒绝外部发送，包括题名／DOI 查询；本地阅读、批注和原文入库可用 |
| 已有普通书库升级后首次使用新策略 | 提示选择策略，不把已有 API Key 自动转换成发送授权；未决策时不启动新的内容发送任务 |
| 文档未单独设置 | 继承所在书库和书架的约束 |
| 文档属于多个书架 | 明确拒绝优先；界面说明是哪一项策略生效，防止移入第二个分类后绕过限制 |
| 敏感上级拒绝、单篇设置允许 | 单篇允许不能静默覆盖上级拒绝；需先显式调整上级策略 |
| CLI／代理无法说明后续联网目标和材料范围 | 在要求严格发送范围的模式下拒绝该渠道，提示选择已支持的服务；不宣称应用能管住任意子进程的全部网络行为 |
| 一次操作涉及多篇论文／多个项目 | 对每个材料源分别检查；任一受限时列出并让用户移除或取消，不能只检查当前选中论文 |

应用更新检查等不发送研究材料的系统通信另列为应用级数据流，不应伪装成论文处理授权；没有声称本功能提供操作系统级防火墙或第三方平台的物理数据驻留保证。

### 4.2 必须盘点的已有数据流

下表是首轮范围，实施前要用实际请求构造和 Python／CLI 启动参数逐条补全；没有盘点完成的发送入口不能被标为“已统一授权”。

| 入口 | 可能发送的数据 | 接收方／边界 | 用户应看到什么 |
| --- | --- | --- | --- |
| 自动题录补全、引文和检索 | 标题、DOI、arXiv ID、检索词；补全 AI 可能还用首页材料 | 题录服务及所选 AI 服务 | 哪些查询字段、是否发送首页材料；敏感库不能先查询再询问 |
| Lee／OCR 导入 | 原 PDF 或 OCR 请求所需的页面内容 | 配置的 OCR 服务；具体载荷随 provider 核对 | 若实际上传整份 PDF，必须显示“整份”，不能描述成仅当前页 |
| 翻译、论文记忆、精读 | OCR 段落、相邻上下文、摘要／更多正文、术语及必要历史 | 全局或实际派生的 AI 渠道 | 页码范围、预计文本范围、服务地址、模型、是否附带上下文或历史 |
| 图表与演示稿 | 选定论文材料、精读结论、图表裁切、用户输入 | 相关 AI 渠道 | 文档清单、图片数量和来源页，不能只显示用户输入的一句话 |
| LaTeX 聊天／修改／修复 | 当前未保存 buffer、项目内其他 TeX／Bib 文件、相关日志和用户问题 | 项目独立模型或全局模型 | 实际文件清单、未保存内容是否参与、日志范围；发送授权与写盘确认分别保留 |
| 自动后台处理／重试 | 前述材料或派生材料 | 已批准的服务，或新目标 | 后台任务也须校验；切换模型、地址、材料范围不能沿用旧的一次性确认 |
| Zotero、同步、分享 | 选择的题录、笔记、附件、研究判断及导出内容 | 本机 Zotero、远端文库、网盘或分享包接收方 | 是否离开本机、具体对象清单、只读／写入动作及被排除字段 |

“数据被发送”与“第三方如何留存”分开说明；后者只能链接已核实的服务政策，不作替第三方保证。不要显示笼统的“已脱敏”，除非将来有明确变换规则、预览和验证。

### 4.3 操作流程与服务端约束

1. 用户点击具体动作，服务端根据实际材料及配置生成发送计划。
2. 计划列出目标服务、模型、数据类别、材料对象和范围；用户可以查看并移除材料。敏感策略拒绝时，停在这里，不做联网题录补全或远端“预检”。
3. 用户选择“仅本次”或在允许范围内保存规则；不能在这个步骤修改调用者无权覆盖的上级策略。
4. 服务端执行时验证计划与策略版本、材料版本和目标服务一致。前端隐藏按钮不算权限执行。
5. 每次外发批次及后台任务恢复前重新检查撤销状态。已完成的网络发送不能因撤销而被描述成已追回。
6. 自动重试仅限批准的范围；备用 provider、扩展到更多文件、引入新的截图都要重新形成授权计划。

建议接口是新接口草案，不表示当前已有：`GET/PATCH /v1/processing-policy`、`POST /v1/processing-preflight`、各动作执行时提交 `planId`。计划应由服务端保存或签名绑定动作参数摘要、实际材料版本、目标和有效期；执行时使用服务端绑定的参数，不相信客户端自行报告的材料摘要。

建议新增明确的 SQLite 表：`processing_policies`、`processing_plans`、`processing_grants`、`processing_audit`。审计记录动作、文档 ID、策略版本、目标、数据类别、数量、结果和时间，不复制正文、密钥、私人题名或源码来“证明发送过”。密钥继续沿用现有系统存储方案，不进入策略或分享数据。

### 4.4 验收条件

- 敏感库拒绝 OCR、AI、自动题录和后台记忆时，相应受控测试接收端收到 **零次材料请求**；不能只断言接口返回 403。
- 直接调用服务端接口、批量动作、后台重试和重启恢复不能绕过策略。
- 撤销授权后不再启动新批次；已在途请求的状态如实说明。
- 模型地址、文件或范围变化后旧计划失效；不受支持的 CLI／工具模式不被标为可精确管控。
- 仅保存原文、阅读和本地批注在拒绝外发时仍可使用；LaTeX 写盘确认不会被发送授权替代。

工作量：**10–15 人日**。这是多个已有发送链路的执行约束，不按“新增一个设置开关”估算。

## 5. P1：多源学术检索与检索式入库

### 5.1 来源和语法

首版候选来源为 PubMed、OpenAlex、Crossref：PubMed 补医学主题检索，OpenAlex 做跨学科发现和后续引文扩展，Crossref 做 DOI 题录发现／核对。每个来源的检索能力单独声明，不把同一个布尔表达式无提示降级成所有来源的关键词串。

提供两种输入：便于常用操作的结构化条件，以及逐源原生检索式。通用条件转换后必须显示实际发出的检索式；不支持的语法明确拒绝或要求用户为该源单独填写。PubMed 支持布尔组合及字段标签，具体语法按其官方指南实现；E-utilities 需按来源限制做节流，不能照搬当前并发导入槽数。[PubMed 用户指南](https://pubmed.ncbi.nlm.nih.gov/help/)、[NLM E-utilities 说明](https://www.nlm.nih.gov/dataguide/eutilities/utilities.html)、[NLM 请求速率说明](https://support.nlm.nih.gov/kbArticle/?pn=KA-05317)。

OpenAlex 的搜索语法和鉴权／额度单独适配，发布前复核，不能沿用“永久无需 key、无限制”的假设。[搜索文档](https://help.openalex.org/api/searching/)、[鉴权文档](https://help.openalex.org/api/authentication/)。Crossref 的元数据接口不等于提供论文全文或对所有摘要授予同一种再分发许可。[REST API](https://www.crossref.org/documentation/retrieve-metadata/rest-api/)、[元数据使用说明](https://www.crossref.org/documentation/retrieve-metadata)。

### 5.2 流程与数据

在现有发现／资讯区域共用“文献检索”入口：选择来源 → 编辑并预览逐源表达式 → 执行 → 查看逐源状态和去重结果 → 批量勾选 → 先保存题录为待读 → 对可获取全文的条目单独下载和处理。

建议数据表：`search_sessions`、`search_source_runs`、`search_hits`、`bibliographic_records`、`record_sources`。保存检索日期、原始输入、逐源实际表达式、筛选条件、适配器版本、返回总数、已抓取数、游标、错误和每条结果来源。数据源会更新，承诺的是保留当次证据，不承诺未来重跑得到相同命中数。

去重优先规范 DOI，再看 PMID／arXiv 等外部标识；题名与作者相似只能提示人工合并。预印本和正式发表版保留版本关联，不靠题名自动折叠。逐源命中数不能简单相加后称为“唯一文献数”；分页未完成、条数上限和某来源失败都需显示。

新题录身份与现有文档／附件通过映射关联，不重新生成旧文档 key，也不据此重写批注和阅读位置的外键。纯题录、已下载附件和已完成全文处理分别显示状态，不能为了统一列表而伪造一个空 PDF 文档。

验收：保存并导出检索记录；至少两源独立失败不影响另一源；同 DOI 多来源保留出处但不重复建文献；无全文结果仍能加入待读；布尔语法转换可通过固定样本比对；不将题录命中宣传成系统综述已完整覆盖领域。

工作量：**10–15 人日**。三源均为目标，但可先交付两源，再接第三源；不能在未交付的来源上显示完成状态。

## 6. P1：引文链扩展发现

复用现有 OpenAlex 引文接入，将“最近 8 条”扩成带分页的结果页。首版提供一个锚点、两个方向（参考文献／引用本文）、用户触发的逐层扩展，不默认递归抓取整张网络。

每次扩展保存种子文献、方向、层数、提供方、查询时间、游标、返回／已解析数量及父子路径。限制可配置的层数、条目数和请求额度；任何截断都披露。相同库外候选复用第五节的身份模型，加入同一待读队列，不另建一个只属于引文图的题录库。

结果标注“来自某目录服务”“全文未验证”，并区分目录未收录、引文关系未解析和结果确实为空。提供“加入待读”和“继续扩展”，全文下载仍经现有导入队列和 P0 校验。没有 DOI 时可尝试让用户选择可靠的外部标识匹配，不凭题名相似自动决定种子身份。

验收：能从一个种子查看库外前作和后续工作，分页、去重、暂停／继续及额度提示有效；保存一次扩展后能回查“从哪篇、哪个方向发现”；不把引文边解释成支持／反驳关系。

工作量：**5–8 人日**，依赖检索结果和来源模型，避免重复建设。

## 7. P1：浏览器一键采集

首版为 Manifest V3 的 Chrome／Edge 扩展，采用用户点击后取得的页面权限，先支持 arXiv 页面、直接 PDF 和带常见学术元数据的论文页。不要以安装扩展为由取得所有网站的永久读取权限；`activeTab` 的访问由用户操作触发，适合作为首版权限基础。[Chrome activeTab 官方说明](https://developer.chrome.com/docs/extensions/develop/concepts/activeTab)。

采集对象限于页面 URL、题录元标签、DOI／arXiv ID、可用 PDF 链接及用户明确选中的文字；默认不复制整页 DOM、Cookie、浏览历史或登录凭据。页面里的数据不可信，服务器需验证协议、大小、字段及 PDF 获取地址。

### 7.1 与桌面端连接

优先设计 Native Messaging 的桥接原型，以处理桌面端动态端口和扩展身份验证；正式选型须验证 Windows／macOS 的安装与主机注册。若评估后采用本地 HTTP，必须有用户配对、受限权限和明确扩展来源检查，不能把现有全权限后端 Bearer Token发给扩展或普通网页。

扩展仅获得提交采集候选和查询自身提交状态的权限，不允许调用 AI、删除文献或读取整库。桌面未运行时可以本地暂存少量采集候选，显示“等待发送”；不得伪装成已经入库。安装包需提供桥接安装／卸载和版本兼容路径。

### 7.2 入库与验收

采集提交先进入桌面“采集收件箱”，显示来源页面、发现时间、候选题录、PDF 状态及重复候选。用户确认后复用现有队列；自动题录查询、全文处理必须经过 P0。需要登录或订阅才能下载的内容只保存来源与题录，提示用户自行通过已有合法访问方式取得文件。

验收：Chrome／Edge 点击一次能保存来源候选；桌面关闭和重开后可继续；错误网页不能调用任意后端接口；重复点击不重复入库；首次配对、撤销、动态端口和两平台安装路径可验证。首版“点击即采集”表示进收件箱，不表示页面必然可下载全文或免除首次授权。

工作量：**8–12 人日**。扩展商店分发审核及 macOS 主机注册的实机条件另列，不藏进乐观估算。

## 8. P1：只读分享包

首版支持“选中文献＋选定批注／存疑＋精读章节＋已有对照结论”的内容选择，不新增一套研究判断编辑器。分享前预览清单，默认只含题录及用户选择的可分享研究产物；包含原文、图表、私人笔记必须逐类明确选择，并受 P0 约束。

### 8.1 格式和查看器

定义独立版本格式 `.readxshare`，含 `manifest.json`、题录、已选择的证据和可选附件。分享 DTO 采用字段白名单，不能从完整备份复制整个数据库、配置、浏览器存储或项目目录。绝对路径、密钥、任务日志、聊天历史、未选择的草稿和源码均不进入首版包。

交付附带离线 `viewer.html`：接收方解包后打开查看器，主动选择分享数据包，由 File API 读取。这个流程避免依赖 `file://` 下的自动 fetch、模块或 worker 行为；PDF.js、字体和脚本全部随查看器打包，目标浏览器以 Chrome／Edge 桌面端为首版，不需要账号或安装 ReadX。

按 PDF 原始页号跳转；书面页码标签另列。未附原文时显示来源、页码和允许分享的引文，不能显示成可查看的完整上下文。图表显示来源页与裁切范围；EPUB 位置仍用章节定位，不伪造成 PDF 页码。

只读查看器无 AI、同步、自动远端图片或远端字体请求；Markdown／HTML 内容按不可信数据处理，禁止执行包内任意脚本。读者可复制已选择公开给他的内容，“只读”不是 DRM 或防截屏保证。

### 8.2 验收

- 默认导出清单中没有任何凭据、绝对路径、浏览器本地状态、未选笔记或项目源码。
- 断网、未安装 ReadX 的目标浏览器可浏览和跳到所含 PDF 的指定页；没有原文时明确说明。
- 包损坏、版本不支持、附件过大和缺文件会显示具体错误；大包限制应基于原型测量后固定，并给出仅导出题录／笔记的替代选项。
- 外部链接只在读者点击后跳出；分享导出权限不自动证明论文全文具有再分发许可。记录用户的包含选择及可获得的许可信息，不替用户自动作法律判断。

工作量：**8–12 人日**。可在完整 Zotero 双向同步之前独立交付。

## 9. P1：Zotero 完整迁移与双向回写

这是两次交付，不以“PDF 能导入”宣称完整迁移，也不把“写回一个笔记”宣称全字段双向同步。

### 9.1 Z1：完整单向迁移

扩展现有本机只读接入，列出并迁移用户选中的题录、集合树及成员关系、标签、笔记、可获取的附件和支持的批注类型。文档可以属于多个集合；多个 PDF、EPUB、笔记和其他附件不应被压成一个 `pdf_path` 字段。

新增映射身份采用 `(connector, libraryId, objectType, objectKey)`，保存条目版本、父子关系、最后导入版本、本地对象 ID 及内容指纹。同 DOI 只能帮助判重，不能代替 Zotero 对象身份。现有浏览器收件箱、检索来源与 Zotero 来源都指向同一本地文献身份。

支持迁移预演：显示可迁移对象数、附件可用性、格式不支持项、冲突及预计文件量；实际迁移可取消、断点继续、幂等重跑。每种不支持对象给出明确清单，不静默丢弃。链接附件或仅云端存在的文件需要按实际能力获取，不能从题录字段推定文件已到达本机。

验收以固定样本库对比集合树、成员关系、笔记、附件数量和内容；失败重跑不重复创建对象，取消后已完成对象可核对，原 Zotero 库不被修改。

工作量：**10–15 人日**。

### 9.2 Z2：受控回写，再交付持续双向

先写回用户明确选择的 ReadX 笔记／精读摘要和阅读状态：建议把摘要保存为带来源标记的子笔记，状态使用可配置的命名空间标签，不覆盖原作者笔记或将自定义状态硬塞到标准字段。原生 PDF 批注需另验证页码、选区、附件版本与批注类型，无法无损转换时说明差异，不伪装成原生等价。

授权渠道需要运行时探测。官方当前文档说明：Web API 写入需要具备文库写权限的 key；Zotero 10+ 的 Local API 也提供写入能力并有本机授权与版本前置条件。这与当前 ReadX 只读接入是不同能力，不能由旧文案“7+ 可读”推定可写，也不能永远假定本地 API 只有只读。[Zotero 写请求](https://www.zotero.org/support/dev/web_api/v3/write_requests)、[Local API](https://www.zotero.org/support/dev/web_api/v3/local_api)。

首选在目标客户端具备能力时使用明确授权的本机接口；否则用户可单独选择云 Web API 路径，并看到数据离开本机的说明。不得直接修改 Zotero 数据库，也不在无云授权时自动降级到远端写入。

持续双向采用“最后同步基线＋本地版本＋远端版本”的三方比较，并使用 provider 的版本前置条件写入。冲突进入待确认队列；不以最后写入时间盲目覆盖。首版不传播永久删除：外部删除先标为来源缺失，本地删除不自动删除 Zotero 对象。保存变更来源和操作 ID，避免回写内容被再次导入后反复生成新笔记。

回写前预览，批量操作可停止；校验版本冲突、重复提交、远端修改后重试以及部分成功。撤销授权后停止后续请求，不声称能够撤销已成功的远端修改。

工作量：**15–25 人日**，其中原生批注兼容若不能在样本上达标，应明确降为独立笔记交付，并重新评估“完整双向”范围，不能用降级版本冒充全量完成。

## 10. 建议排期和里程碑

### 10.1 单人线性排期

| 顺序 | 里程碑 | 工作量 | 可独立验收的结果 |
| --- | --- | --- | --- |
| M1 | P0 授权与数据流 | 10–15 人日 | 敏感库默认拒绝；已盘点路径服务端执行权限；本次发送说明和撤销有效 |
| M2 | 多源检索与身份／来源基础 | 10–15 人日 | 保存检索式、逐源统计、批量选题录入库及可说明的去重 |
| M3 | 引文滚雪球 | 5–8 人日 | 库外关系分页、发现路径、扩展预算与加入待读 |
| M4 | 浏览器采集 | 8–12 人日 | Chrome／Edge → 配对桥接 → 收件箱 → 现有导入队列 |
| M5 | 只读分享 | 8–12 人日 | 可选择内容的分享包和断网可用的独立查看器 |
| M6 | Zotero Z1 单向迁移 | 10–15 人日 | 集合、笔记、附件等选定范围的迁移预演与可靠重跑 |
| M7 | Zotero Z2 回写／双向 | 15–25 人日 | 有授权、有对象映射、有版本冲突处理的限定范围同步 |
| 合计 | 六项能力，Zotero 分两次交付 | **66–102 人日** | 不以单一“大版本全部上线”作为唯一交付方式 |

预留约 15% 集成与第三方适配缓冲，约 **10–16 人日**；总计划约 **76–118 人日，即 16–24 个工作周**。这是单人串行的初步范围估算，不是承诺发布日期。

建议首个可用版本只包含 M1；若希望尽快验证研究发现闭环，随后交付 M2＋M3。前三个里程碑合计 25–38 人日，加相应缓冲约为 **6–9 周**。M4／M5 可以根据真实用户需求调换；Zotero 可先完成 Z1，Z2 不阻塞其他功能发布。

若投入第二名开发者，比较适合在共用模型稳定后分别负责浏览器扩展或分享查看器；不直接把总工期除以二。策略、身份、接口和跨平台验收仍是共同依赖。

### 10.2 每个里程碑的完成条件

每次交付都应有：实现范围与不支持项、迁移说明、API／数据契约、失败和取消测试、Windows／macOS 验证结果及用户说明。第三方来源适配需记录核对日期、请求限流、所需授权、返回数据许可信息和已知覆盖限制；没有核实的条款标为发布前阻塞项，不写成已经获得许可。

现有审查中尚未解决的数据与任务问题要进入相关里程碑的验收：Zotero 迁移／回写不能依赖可能双跑并覆盖旧数据的作业；浏览器批量入库应复用已修复的同 key 去重；新任务不能复用无限重试且没有错误态的界面。具体必要修复计入相应里程碑或单独标出增量，不默默扩成一次全仓架构重写。

## 11. 开工前需锁定的产品决策

以下有默认建议，可先用于原型和接口草案；正式开工应写进范围记录，不在代码中隐式决定：

| 决策 | 默认建议 | 改变时的影响 |
| --- | --- | --- |
| 权限边界 | 数据根书库＋书架＋单篇；LaTeX 独立项目 | 如需真正多书库实例，必须补库 ID 与跨库操作模型 |
| P0 旧库迁移 | 首次选择策略，不把 API 配置当成同意 | 若要求升级后自动继续后台任务，必须明确如何获得材料发送授权 |
