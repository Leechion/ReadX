## 1. 阅读口径

- **已修复**：已有相应代码变更及记录，不再归入“不修改”。只表示表中列出的范围，不能扩大为整条架构建议已经落地。
- **部分采纳／调整方案**：承认具体问题，但原建议会破坏现有能力、遗漏兼容要求，或与实际调用链不符，采用更具体的修复。
- **待修复**：仍有合理缺陷依据。暂未实施是整改进度，不是拒绝修复，也不表示风险可接受。
- **待核实**：尚不能从报告或本轮检查确认全部触发条件；先复现或补调用链，再确定改动。不据此否定风险。
- **延后重构**：维护性问题成立，但不直接证明当前用户功能错误；需要单独定义迁移范围和行为验收，不在缺陷修复中整批重写。

报告以 `8d85285` 为基线，后续未提交修复以及新增备份、原文导入能力不在该基线内。本文件综合报告与当前修复记录；未重新独立验证的条目明确保留“待核实”。没有使用原报告的文件数量、行数或严重度来代替功能证据。

**编号校对**：正文包含 F1–F24、P1–P8、A1–A15、AP1–AP2、D1–D13，共 **62 项**。摘要称设计问题 14 项、总计 63 项，与正文编号不一致；不存在可据正文确认的 D14。本文件按实际编号覆盖，不补造条目。

### 两处重要的方案调整依据

**F1：不采纳“一律拒绝回环和私网 AI 地址”。** [AISettingsDialog.tsx](../windows/apps/web/src/components/AISettingsDialog.tsx) 明确将本地模型纳入 OpenAI 兼容渠道。模型接口访问用户配置的本地服务，与论文 URL 导入仅访问公共资源的职责不同。套用同一公共网络白名单会使本地模型失效。目前针对已确认的密钥跨来源重定向路径使用 [ai/http.go](../windows/apps/server/internal/ai/http.go) 约束；不据此推定任意初始地址都没有风险。云元数据地址、URL 凭据以及其他 AI 出站路径是否需要额外限制，应另做逐路径核实。

**F2：不采纳“把业务回调整体包进 SQLite 事务”。** [ideas.go](../windows/apps/server/internal/httpapi/ideas.go) 的更新回调会执行证据校验并查询同一数据库；在当前单连接设置下，把回调放在持有连接的事务内可能自锁。因此在 [appstate_store.go](../windows/apps/server/internal/httpapi/appstate_store.go) 采用条件 UPDATE／INSERT，冲突后重新读取并计算，回调保持可查询但不得产生外部写入副作用。另外，[sync.go](../windows/apps/server/internal/httpapi/sync.go) 原本就有事务内快照对比，报告“同步完全没有重读保护”的论证需要修正；这不否定已修复的读改写与同步事务交错问题。

## 3. 尚未完成的功能项及理由

| F19 页边笔记拖动失败无提示 | 待修复 | 需要补可见错误并明确失败预览与服务端已保存几何的区别。直接永久保留未保存的预览也可能误导用户；不采纳这一未经区分的交互，但失败不提示本身仍应修。 |

## 4. 潜在风险的处理理由

这些项在原报告中本就标为潜在风险。本文件不把“尚未复现”改写成“没有问题”。

| 编号 | 当前处置 | 不直接按原建议修改的理由／后续要求 |
| --- | --- | --- |
| P1 Windows 设备名和 ADS | 待核实并修补 | 已有路径边界不能代替设备名、冒号及真实 NTFS 行为验证。应先补相应路径测试，再收紧组件校验；不是因未出事故而接受潜在绕过。 |
| P2 代理场景私网检查 | 待核实 | 必须区分拨号到代理与代理访问目标这两个地址。需要带受控代理的测试，并确认当前客户端实际采用哪一层校验；不能只凭配置代理推定已发生绕过，也不能只验证代理 IP 就关闭问题。 |
| P3 停服残留后端 | 待修复 | 新备份 worker 会等父进程和后端退出，超时则不操作数据；这只是备份流程的保护，不等于桌面停服已补齐强杀和最终等待。后端卡住的故障注入及退出升级逻辑仍需实现。 |
| P4 Windows 下载缺少总超时 | 待核实并整改 | 需区分绝对时限、无进度超时以及用户取消，并确保超时后下载器真正停止，不能只让外层 Promise 提前失败。未复现永久挂起不能作为永久不改的理由。 |
| P5 DMG 哈希不能证明作者身份 | 部分接受，需外部流程决策 | 完整性校验与发布者身份验证是不同保证，不能把前者直接判成毫无作用，也不能称其已验证发布者。签名、公证或带外公钥涉及发布基础设施，不能由本地代码临时生成一个公钥假装解决；应核对界面文案并单独安排发布信任方案。 |
| P6 导入 SSE 坏帧 | 待核实，调整方案 | “跳过所有坏帧”不一定正确：若跳过的是某个文件唯一的结果帧，继续也可能漏报成功／失败。需要验证分包与截断是否真被解析成完整行，并定义缺结果时如何核对书库；不直接复制其他 SSE 端点的容错策略。 |
| P7 全量 Go 测试无输出 | 验证缺口，不作源码缺陷 | 没有定位到具体挂起测试或网络步骤，不能据此修改业务代码。定点测试通过也不能替代全量回归。应使用超时、结构化测试输出和明确代理配置重新定位。 |
| P8 就绪 JSON 缺少字段校验 | 待核实／小幅改进候选 | 当前协议来自自有后端，风险与不可信网络输入不同；仍可通过故障注入证明错误提示缺口。应复用校验逻辑，不需要据此扩张成新的启动框架。未在本轮实现。 |

## 5. 架构项：哪些保留，哪些延后

| 编号 | 当前处置 | 理由与后续条件 |
| --- | --- | --- |
| A1 大 httpapi 包 | 延后分域重构；不接受仅凭大小定“严重” | 大包和职责集中是维护成本证据，不是当前错误行为的完整证据。Service 类型数量也不能衡量全部模块边界。优先让具体缺陷有独立责任层与测试，再按域提取；不一次重写全部 handler。 |
| A2 多存储及重复字段 | 部分接受，延后模型迁移 | 原文文件、派生缓存、关系索引和浏览器偏好本来就可能使用不同存储。需要证明的是同一字段的权威来源冲突，而不是存储种类多。迁移前应列字段权威表、兼容读写与恢复方案，避免新增列后形成另一份真相源。 |
| A3 Store 旁路 SQL | 具体竞态已修；不采纳一律禁裸 SQL | 同步和回收站有跨多表事务，把其中每条 SQL 拆成独立 Store 操作可能破坏事务边界。当前用条件写入防止本地读改写覆盖这些事务。后续可做支持事务上下文的存储层，而非仅靠字符串检查封禁所有 SQL。 |
| A4 迁移至 tasks.Registry | 部分采纳，整体迁移延后 | 同 key 去重已做。注册表“重启恢复”是标失败，不是续跑；终态 TTL 也不等于用户历史保留策略。迁移前需逐项映射持久化、历史、取消、部分产物及文档关联；不能只换类型就认为获得全部能力。容量及清理仍是待处理项。 |
| A5 CI 没跑一致性检查 | 待修复，无永久不改理由 | 文档声称有 CI 闸门而 workflow 未提供，应该纠正。接入前需修正检查范围和换行判据，以免把已知假阳性当成构建失败。本轮尚未修改 CI。 |
| A6 scripts 覆盖不全 | 接受具体遗漏，调整描述 | 已有公共脚本白名单，不能说整个 scripts 完全不受管理。应补公共脚本、明确平台专属脚本和差异，再修真实测试漂移；直接整目录镜像可能覆盖 PowerShell／macOS 专属安装、启动和打包脚本。 |
| A7 列表触发状态重算 | 接受性能问题，暂缓删除调用 | 已核对全库重算调用。报告的“N 次写入”应更准确地表述为 N 次 UPDATE 执行；SQL 有 `status<>?` 条件，未必每篇都产生数据变更。直接删掉重算会丢掉旧数据的状态补算；需先覆盖所有写入点和首次迁移，再将列表改为纯读。依据：[reading_status.go](../windows/apps/server/internal/httpapi/reading_status.go)。 |
| A8 多种哈希与多处取数 | 部分接受，拒绝直接统一哈希 | 页文本指纹、段落原文指纹、带模型／上下文的译文缓存键承担不同职责。不同哈希不自动等于错误；缓存键如果删掉模型信息反而可能复用错误译文。可以收敛访问入口，但需保留各指纹含义及旧缓存兼容。依据：[translation_store.go](../windows/apps/server/internal/httpapi/translation_store.go)。 |
| A9 旧目录与内部 v2 名称 | 部分接受，清理与改名分开 | 用户已明确要求删除本地旧目录；此前执行策略拒绝了删除，未获得成功删除的证据。不能在此记录中写成已清理。Go 模块、环境变量和引导标记是兼容接口，产品名称不同不构成必须立刻整体更名的理由。 |
| A10 运行时资源定位 | 待逐路径核实，延后整合 | 本地开发、源码运行和打包运行会有不同资源位置。需先用路径诊断证明某两个调用实际选到了不同版本；不能直接删候选目录或按文件名统一。报告中的平台硬编码应独立验证。 |
| A11 未调用的旧渲染路径 | 待确认调用图后清理 | 如果确无调用，可删除以降低维护成本；但“未来接回来会复用旧文件”不能当成当前正在发布错误产物的证据。应区分死代码清理与线上缓存缺陷，尚未实施删除。 |
| A12 两端测试命令不对称 | 待修复公共测试遗漏 | 平台打包与原生 smoke 命令可以不同，公共业务回归不应因此漏测。需要抽公共测试列表或补齐明确遗漏；不宜强制两个 package.json 的全部 scripts 相同。 |
| A13 发布脚本多语言及重复步骤 | 延后有范围的重构 | PowerShell 与 macOS 脚本不同不直接证明资源有遗漏。应先建立实际发布资源对照和打包验证，再抽确实重复的数据或步骤；不为统一语言迁移全部安装逻辑。 |
| A14 多渠道配置 | 部分接受，延后配置迁移 | 类型化 Settings 与集中读写有价值，但配置文件、数据库、环境覆盖和系统凭据有不同生命周期。统一结构需保留未知字段、既有密钥命名空间及覆盖优先级；不直接把所有配置搬到一处。 |
| A15 关键模块“零测试” | 不接受判断方法，保留覆盖改进 | 无同名测试文件不代表无测试。[mineru_import_test.go](../windows/apps/server/internal/httpapi/mineru_import_test.go) 会调用 Lee 导入；进度、取消、元数据并发、同步等也有跨文件测试。不能据此宣称覆盖充分，应按函数和失败场景列缺口，而不是按文件名统计“零测试”；不把提取 Service 作为每个修复的前置要求。 |
| AP1 追加式迁移缺少未来回滚模板 | 待规划，不作为已发生迁移丢失 | 增量 DDL 加事务是合理现状，未出现改列需求不需要预造拆表迁移。新增完整备份不等于迁移前自动快照已经实现。真正涉及破坏性迁移时，仍需一致快照、版本检查和恢复演练；不能在 WAL 模式下仅复制主 `.db` 文件。 |
| AP2 vendor 体积与受管镜像 | 部分接受，暂不整体移出 | Rust API 不在启动链不代表整个 vendor 都无用；Lee 的 Python 流水线及相关资源在使用。需按运行时导入、打包依赖及许可证清单区分可删内容，再决定精简、外部下载或子模块。不能用应用层关键词出现次数证明可安全删除。 |

## 6. 设计项：不按原建议直接修改的理由

| 编号 | 当前处置 | 理由与后续条件 |
| --- | --- | --- |
| D1 全部响应统一包络 | 不采纳全量改包络；状态码缺陷另修 | 对象 GET 与集合列表有不同形状可以是稳定契约，不会自动妨碍统一错误处理。整体改成 `{data,error}` 会同时破坏大量现有客户端。应先解决错误码和异常语义不一致，再为新接口明确约定；不把裸数字风格问题与业务错误混为一项。 |
| D2 deleted_at 列 | 延后模型迁移，保留问题 | 单加一列不会让所有查询自动过滤，双写期间可能多一份删除状态。应先确认读路径是否真的漏过滤，再设计迁移和单一权威来源。已确认遗漏需直接修，不必等大迁移。 |
| D3 重复路由与状态来源 | 部分接受，暂不合并所有入口 | 全局任务列表和单文档任务接口面向不同查询；`/pdf` 的兼容别名也不天然是缺陷。应列出实际重复语义及废弃计划，保留旧客户端兼容。任务存储、内存句柄与磁盘产物须定义权威边界，而非强行只剩一种介质。 |
| D4 provider 单一注册表 | 调整方案，暂不强行放 shared | Go 不能直接 import TS 注册表；需要独立数据或代码生成才能真正跨语言复用。HTTP、CLI、登录渠道及 LaTeX 支持集合也可能有明确能力差异。应按能力声明和契约测试收敛，避免“共用清单”错误开放不支持的渠道。 |
| D5 换行导致漂移假阳性 | 接受问题，调整检查方案 | 不能直接比较 `git show HEAD:` 来验证尚未提交的改动，因为那会漏掉本轮工作区变化。应按文本／二进制类型处理工作区内容，遵循属性规则；不能对所有二进制文件全局替换 CRLF。当前尚未改检查器。 |
| D6 拆分 API 客户端 | 延后结构重构 | SSE 和错误码的已确认行为差异已经单独修复，文件变大本身不要求立即拆全部资源模块。后续拆分应保持 API 导出和鉴权语义，不在缺陷修复中同时改所有调用路径。 |
| D7 拆组件／引入 Context | 延后按职责重构 | 行数和 props 数量是维护信号，不足以单独证明需要新全局 store。先围绕轮询、导航和持久化定义边界，再抽重复逻辑；避免一次重构改变阅读位置、选区与双栏同步行为。 |
| D8 统一 localStorage 包装 | 部分接受，保留各数据 schema | 通用 JSON 解析包装不等于能校验聊天、版式和文库等不同结构。替换时须保留现有结构校验、旧键回退、写入失败提示；不能仅将所有读取机械替换为 `readJSON` 后视为安全。 |
| D9 LaTeX Service 单例与全局 registry | 待核实生命周期，延后整合 | 将 registry 变成实例字段却继续每请求 NewService 会丢失共享取消状态；先确立 Server 单例服务与测试隔离，再迁移状态。应以多实例互相影响的复现验证缺陷，不能只改结构声明。 |
| D10 私网判定收敛 | 待核实并整改，保留场景差异 | 公共书源的网络判定值得复用，但应同时检查目标解析、拨号、代理与重定向，不能只换一个 IP 函数就宣称修好。也不应顺带把允许本地模型的 AI 渠道套进相同公共资源规则。 |
| D11 通配动作路由 | 接受可读性改进，低优先级 | handler 已返回 405 的情况下，尚无证据表明错误动词会执行动作；当前主要是路由契约与文档清晰度问题。显式路由可以后续调整，不能按实际授权绕过计。 |
| D12 产品与模块名称 | 暂不整体改名 | 包名、Go import、环境变量、就绪标记和产品展示名不必一致。整体更名需要兼容层，并核对脚本、已有配置及旧启动器；不能为了消除 v2 字样破坏工作环境。就绪常量重复可单独用测试或生成方案约束。 |
| D13 文档与代码漂移 | 接受，待针对性修订 | “CI 已强制”及多趟上限矛盾应修正文档。仅增加一个泛化的文档一致性检查无法证明所有叙述正确；应先改具体事实、链接实际 workflow 与常量，再决定哪些断言值得自动检查。当前没有理由永久保留错误说明，本轮仅记录，尚未修改架构文档。 |

## 7. 后续处理顺序

1. 优先处理仍会导致数据损失或错误交付的项：F12、F10／F24、F23，以及 F22 的引导通道迁移。
2. 处理可见失败与恢复：F8、F18、F16、F19，并补对实际失败场景的验证。
3. 修复平台一致性保障：A5／A6／A12／D5／D13，先确认判据和公共文件清单，再接 CI。
4. 再按真实瓶颈处理 F13／F15／F17／A7，以及按域推进架构重构。F20 等独立小缺陷不必等结构迁移。

以上是基于现有证据的建议顺序，不表示其他项已接受风险或关闭。需要跨平台运行时、代理、更新器或发布基础设施才能确认的项，仍保留验证条件。
